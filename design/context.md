# Chorus 产品与界面改版上下文

## 目标

把 Chorus 从“功能较多但部分链路只在代码层存在”的工程 Alpha，收敛成一个真实可用、状态可信、可恢复的本地 Agent 通信工作台。

核心结果不是增加页面数量，而是让用户能够完成以下任务：

1. 首次打开后发现或添加一个 Agent，并完成第一轮对话。
2. 在单聊中可靠地发送、停止、重试并理解错误。
3. 创建多 Agent 会话，明确选择接收者，并看懂 A2A 的路由、进度与结果。
4. 配置跨设备连接，安全建立联系人关系，再由各自所有者把 Agent 加入 Room。
5. 长期管理会话、Agent、联系人、权限、诊断和本地数据。

## 用户

- 核心用户：同时使用 Claude Code、Codex、Gemini CLI 等本机 AI CLI 的开发者。
- 扩展用户：希望让不同设备或同事的 Agent 在明确授权下协作的小团队。
- 使用环境：以 macOS、Windows 桌面端为主；浏览器开发模式用于调试，不作为完整跨设备产品承诺。

## 约束

- 保留 React + Vite + Zustand + Fastify + SQLite + Tauri 技术栈。
- local-first；本地单人能力不依赖 Chorus 账号或 Relay。
- 不把远程联系人自动等同于可调用 Agent。
- 不以静默广播或自动加入 Room 换取“看起来更顺畅”的体验。
- 中英文、明暗主题、键盘操作和小窗口必须可用。
- Evir 仅作为质量标准参考：语义 Token、完整状态矩阵、真实渲染验证、失败恢复和证据分级；不复制其 Agent 模式或 Provider 产品模型。

## 成功标准

- 首次用户在 3 个主步骤内进入可聊天状态：发现/添加 Agent → 建立会话 → 发送消息。
- 所有用户发起的异步操作在 200ms 内显示 pending 反馈，并在失败时提供具体原因和至少一个恢复动作。
- 不存在“只写 console/logger、界面无反馈”的核心操作失败。
- 配对不会泄露 Agent；Room 邀请必须由接收者接受；只有所有者可添加自己的 Agent。
- 375×812、800×600、1280×800、1440×900 均无核心操作被遮挡或不可达。
- Light/Dark 下正文对比度达到 WCAG AA，所有图标按钮有可访问名称和可见焦点。
- 产品状态区分：代码存在、自动测试通过、浏览器渲染通过、原生桌面通过、真实双设备通过。

## 本轮范围

- 全用户旅程和状态闭环审计。
- 修复 P0/P1 产品逻辑和反馈缺陷。
- 重构视觉 Token、导航、聊天、设置、弹窗、空/加载/错误/权限/离线状态。
- 设计并接入适合 Chorus 的应用图标。
- 建立可重复的页面清单、状态矩阵和视觉验收。

## 非目标

- 新增 Chorus 云账号或官方 SaaS。
- 把尚未完成的协议包装成“已连接”或“已加密”。
- 为追求视觉变化替换技术栈或删除现有功能。
- 复制 Evir 的工作区 Agent、Provider 或权限模式。

## 已知事实与假设

- 事实：当前本地聊天、Agent 发现、A2A、Relay/P2P 基础代码已经存在。
- 事实：当前 Web 和 Relay 没有独立测试套件，浏览器 E2E 缺失。
- 事实：当前生产桌面后端依赖系统 Node 和未打包的运行依赖。
- 事实：当前 API 默认监听所有网卡且关闭认证。
- 假设：用户更关心“当前协作与消息”而不是按 Agent 展开的多层历史树，因此推荐 conversation-first 导航。
- 假设：跨设备能力在首发中仍是核心，而不是隐藏到实验功能。

## 风险

- 跨设备配对和 Room 邀请涉及协议状态，不是纯 UI 改动。
- 现有超大组件会放大回归风险，需要先拆分公共状态与导航组件。
- 没有真实双设备环境时只能完成实现和确定性验证，不能宣称真实跨设备闭环已通过。
